# Project Context

This document describes what the Futscout API repository is and what it serves.

It exists so that AI agents do not hallucinate scope (e.g. "let me build the React screen for this") or invent integrations that do not exist.

---

# What This Repository Is

Futscout API is a **backend-only Node.js HTTP API** that powers the Futscout platform — a product for young football athletes, observers (scouts), and the internal admin team.

- Repository path: `~/projects/futscout-api`
- Runtime: Node 20+, Fastify 5, TypeScript ESM
- Persistence: PostgreSQL via Prisma 6
- Local DB: Docker Compose (`futscout-api-pg`)

There is **no frontend code in this repository**.

The athlete mobile app and the observer web app are separate projects that consume this API. The endpoints being added to serve the admin surface also live here — there is no separate admin backend.

---

# Product Surface (consumers of this API)

The API currently serves three audiences:

1. **Athlete app** — mobile app where athletes manage their profile, teams, competitions, matches, plays (videos), achievements. Most authenticated routes under `/api/athletes/*`, `/api/matches/*`, `/api/plays/*`, `/api/achievements/*`, `/api/videos/*`.
2. **Observer app** — web app for scouts. Routes under `/api/observer/*`, plus public discovery routes (`/api/public/athletes`, `/api/public/athletes/:id`) and saved searches (`/api/saved-searches/*`).
3. **Admin surface (this workstream)** — internal tools that will consume the new endpoints added under this workstream. Keep admin endpoints under a clearly scoped prefix (e.g. `/api/admin/*`) and guard them with role checks (`role === 'ADMIN'`) on top of `verifyJwt`.

Agents must not build UI for any of these audiences from this repo.

# Domain Model (already in place)

The Prisma schema at `prisma/schema.prisma` defines the canonical domain. Agents must read it before introducing new fields, enums, or relations. Key domain entities include:

- **User** — authentication identity. Roles: `ATHLETE`, `OBSERVER`, `ADMIN`. Supports email+password and social login (Google, Apple).
- **AthleteProfile** — the public athlete identity: slug, category (U5–U20, AMATEUR, PROFESSIONAL), position, dominant foot, height/weight, current club, etc.
- **ObserverProfile** — the scout identity.
- **Team** and **TeamHistory** — teams the athlete has played for (with `isPrincipal` flag for current club).
- **Competition** — tournaments and championships.
- **Match** — a single game. Has `MatchStatus` (SCHEDULED, LIVE, FINISHED, CANCELLED), `MatchResult` (WIN/LOSS/DRAW/NOT_FINISHED), `Modality` (FUT_11, FUT_7, FUTSAL).
- **Play** — a tagged moment inside a match OR a standalone video. `PlayType` is a rich enum (GOAL, DIFFICULT_SAVE, ASSIST, DRIBBLE, FREE_KICK, etc.). Plays carry a video URL hosted in Cloudflare R2.
- **Scout** — per-match or per-position aggregated stats, optionally generated by AI.
- **Achievement** — titles and awards, `COLLECTIVE` or `INDIVIDUAL`.
- **Favorite** — observer→athlete or athlete→athlete bookmarks.
- **SavedSearch** — observer-only persisted filters.
- **Plan / Subscription / Usage** — Stripe-backed billing plus monthly usage counters.

Admin endpoints should read from and write to these existing tables rather than introducing parallel structures.

# Data Imports

There is a CSV-driven data-import workflow under `scripts/`. It matters for admin work because the admin UI will likely surface imported records.

Order of execution:

1. `npm run db:import-atletas` — imports athletes from `data/atletas.csv`.
2. `npm run db:normalizar-nomes` — normalizes names to Portuguese title case.
3. `npm run db:import-partidas` — imports match data and goal plays from `data/partidas.csv`.

Imported plays do **not** have a video URL attached (see commit `23d1d93`). If admin features expose plays, treat `videoUrl === null` as a valid state for imported goals.

# Authentication

- JWT access token (`env.JWT_EXPIRES_IN`, default `15m`) signed via `@fastify/jwt`.
- Refresh token stored in `RefreshToken` table with a DB-tracked `expiresAt` (default 30 days).
- Logout writes the access token into a blacklist (`prisma-token-blacklist-repository.ts`). The `verifyJwt` middleware checks that blacklist on every protected request — any admin feature inherits this behavior for free.
- Login credentials can be **email OR CPF**. The authenticate controller normalizes CPFs via `normalizeCpf` (strip non-digits, zero-pad to 11). Reuse this when adding admin "impersonate" or "find user" endpoints.
- Social login: Google and Apple, via `google-auth-library` and `apple-signin-auth`. Client IDs come from `GOOGLE_CLIENT_IDS` / `APPLE_CLIENT_IDS` env vars.

# Billing (Stripe)

Billing is first-class in this codebase and admin screens will surface billing state.

- `Plan` rows are seeded at server startup by `seedPlans()` in `src/setup/plans.ts`. FREE and PREMIUM are always present; monthly limits on FREE are kept in sync on every boot.
- `Subscription` is linked to a Stripe subscription and includes `status`, `currentPeriodEnd`, Stripe customer id, Stripe price id.
- `Usage` is a per-user / per-month counter row used by the `checkUsage` middleware.
- The Stripe webhook (`POST /api/billing/webhook`) **requires the raw body** — `config.rawBody = true` is set in `src/http/routes.ts`. Do not introduce any JSON-parsing middleware that would consume this.
- `docs/ALINHAR-AMBIENTES-STRIPE.md` documents how test/prod Stripe environments must be aligned. The `scripts/` folder contains one-shot maintenance scripts (`verificar-ambiente-stripe.ts`, `atualizar-customer-id.ts`, `tornar-usuario-premium.ts`, etc.). Admin tooling should prefer these existing scripts over ad-hoc SQL.

# Media Storage (Cloudflare R2)

All media (profile photos, play videos, thumbnails) lives in **Cloudflare R2** using the S3-compatible API.

- Wrapper: `src/lib/cloudflare-r2.ts`. AWS SDK is used with R2 endpoint credentials.
- Preferred upload flow: generate a presigned URL (`GET /api/videos/upload-url`) → client uploads directly to R2 → client calls `PUT /api/plays/:playId/video-url` with the final URL. This avoids streaming large files through the API process.
- Thumbnail generation and compression use `fluent-ffmpeg` (`src/lib/video-thumbnail.ts`, `src/lib/video-compression.ts`). These require a local `ffmpeg` binary on PATH.
- Admin endpoints that moderate or delete media should delete the R2 object in addition to the DB row, not just one or the other.

# AI (OpenAI)

- `src/lib/openai.ts` wraps the OpenAI SDK.
- Used for generating scouts: `POST /api/matches/:id/scout/ai`.
- `OPENAI_API_KEY` is optional in env; features using it must degrade gracefully when absent.
- AI is an enhancement layer, never a prerequisite for core CRUD flows.

---

# Environment Variables

All env vars are validated by Zod at module load in `src/env/index.ts`. Required:

- `JWT_SECRET`
- `DATABASE_URL`

Optional but commonly used: `DATABASE_URL_TEST`, `DATABASE_URL_PROD`, `SMTP_*`, `OPENAI_API_KEY`, `CLOUDFLARE_R2_*`, `GOOGLE_CLIENT_IDS`, `APPLE_CLIENT_IDS`, `STRIPE_*`, `APP_REDIRECT_URL`.

`getDatabaseUrl()` selects the DB URL based on `NODE_ENV` (`dev | test | production`).

# Non-Goals

Agents must not introduce:

- a frontend (React, Next.js, HTML templates, admin dashboards in this repo)
- microservices or a separate admin backend
- an ORM other than Prisma
- a validation library other than Zod
- a DI container
- a background job framework (no BullMQ, no agenda, no temporal) — all "background" work today is synchronous within the request or performed by `scripts/` one-shots
- rate limiting or caching libraries beyond what is already used
- observability stacks (OpenTelemetry, Sentry, Datadog) — logging goes through Fastify's built-in logger

If any of these are genuinely needed, the human must request them explicitly.
